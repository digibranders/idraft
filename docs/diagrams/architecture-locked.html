Visibility Platform Architecture

One host, five services, one ledger. What runs where, how a paid provider call moves from a scheduled row to a number on a screen, and which parts of the original spec were cut.

For: the agency team and client logins Not yet: public SaaS (nothing here blocks it) Target load: 1,000 keywords daily, 1,000 prompts weekly Provider cost: about $102 to $148 a month

Amended 2026-10-31 by ADR-023: host. The host is now a shared Hostinger VPS (4 vCPU, 16 GB, Ubuntu 24.04) with a capped 8 GB idraft share (idraft.slice), a shared host-level edge proxy that owns ports 80 and 443, and a second project on the same machine. Where this page says "droplet", read "the idraft share of the shared VPS". Firewall is Hostinger hPanel plus ufw; the second backup copy is a Hostinger snapshot (verify in hPanel). Process model, Compose, data flow and the cuts below are unchanged. The original text is kept below as history. See ADR-023.

What is locked

Python backendFastAPI for the API, Taskiq for the worker. Extraction and statistics live where the libraries are.
Next.js on the same hostSame origin as the API. Server rendering calls FastAPI over the Docker network, not across the internet.
PostgreSQL 18 is the ledgerObservations are append-only and partitioned monthly. Rollups hold counts and sums. Every number is reproducible.
A task row before every paid callThe scheduler writes the row, the dispatcher checks the budget, then the job is queued. Losing Redis loses nothing.
Redis for transport onlyQueue (acknowledged streams), rate limiter, scheduler lock, session cache. No state lives only in Redis.
DataForSEO behind an adapterSERP, AI Mode and the LLM scraper through one interface, polled every 30 to 60 s. No public callback endpoint.
Raw payloads in R2Every provider response is kept compressed, so a parser fix can re-derive history without paying again.
Measurement rules unchangedDepth profiles, mention and citation kept separate, deterministic extraction first, intervals with denominators, no composite score.
Own auth moduleArgon2 passwords, a sessions table, TOTP for admins, invitations and roles. About 500 lines, no framework to fight.
Tenant isolation staysRow-level security on every workspace table plus a cross-tenant test in CI. Clients log in, so this is not optional.
Docker Compose, images built in CINothing is built on the server. Rollback is the previous image tag.
8 GB share of a shared VPSOriginally a 4 GB droplet at 2.1 to 2.8 GB steady state; now the 8 GB profile on a shared Hostinger VPS. Move to a dedicated 16 GB or 32 GB VPS on defined triggers, not on a hunch.

Deployment

Six containers in the idraft share of one shared Hostinger VPS. A host-level edge proxy (shared with the second project, open decision D-H2) owns ports 80 and 443 and forwards to Caddy, which listens on loopback only; Postgres and Redis have no published ports. The worker is the only process that spends money.

The paid-call lifecycle

This is the mechanism that protects the budget. A provider call exists as a Postgres row before it exists as a Redis job, the budget is checked before the job is queued, and retries move the row, never resubmit blindly.

Data flow

Two collection lanes, one derivation layer, denominators all the way through. The AI Overview is parsed out of the same SERP check that produces the rank, so it costs nothing extra and is stored once.

One Python project with two entrypoints, one Next.js app. The purity rules from the original design are kept and enforced with import-linter: domain and extraction import nothing internal, and providers never touches the database.

Scaling triggers

Decisions are made on measurements, not on a hunch. Each trigger has one action.

TriggerActionCost
idraft.slice memory above 70% of 8 GB for a week, or swap in steady use, or host load average above 3.5 for 15 minutes more than three times a week, or the database over 20 GBMove idraft to its own 16 GB VPS, then 32 GB (doc 28 section 7)verify in hPanel

What happens next

Phase 0, about one week

  • Put the repository under git and commit the baseline.
  • Fund DataForSEO and create the two R2 buckets (yours to do).
  • Spikes S-01 to S-06: SERP task flow and billing, payload sizes, AI Overview async behaviour, ChatGPT and Gemini scraper payloads, replicate independence, AI Mode. Fixtures captured with schema hashes; the price book seeded from confirmed billing.
  • S-09: synthetic 12-month dataset to confirm the partition and index plan. S-11: the canonicalizer on real URLs.
  • Freeze docs 04, 05, 12 and 19.

Phase 1, about three and a half weeks

  • Backend skeleton: FastAPI, SQLAlchemy, Alembic, Taskiq, settings, structured logs, Sentry.
  • Schemas auth, core and ops; row-level security; the task ledger and price book; partition maintenance.
  • Auth: sign-up, sign-in, TOTP for admins, invitations, roles, workspaces, projects, audit log.
  • Worker: scheduler tick, dispatcher with budget check, the DataForSEO client with rate limiting and its error taxonomy.
  • Next.js shell from the design system: auth screens, switcher, settings, empty overview; generated API client.
  • Host bootstrap, Compose stack, Caddy, firewall, GitHub Actions deploy, nightly backup, Healthchecks, uptime ping.
  • Done when: a user signs up, creates a workspace and project, invites a member, and a second workspace cannot see the first; the nightly backup lands in R2 and restores; a deploy from main takes under 10 minutes.
