# App Speed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the measured causes of slow page loads on app.idraft.ai, starting with the ones that need the least code.

**Architecture:** No structural change. Phase 1 adds one database index, gives the API more connections and a second process, and moves OS updates out of working hours. Phase 2 measures where the API burns CPU before any handler is rewritten. Phases 3 to 5 cut the number of requests a page makes; each gets its own plan once Phase 2 has numbers.

**Tech Stack:** PostgreSQL 18, Alembic migrations as raw SQL, FastAPI on uvicorn, SQLAlchemy async with asyncpg, systemd on Ubuntu 24.04, Next.js 16 with TanStack Query.

### Task 1: Index for the country lookup

`prompt_location_id()` in `backend/src/idraft/keywords/prompt_links.py:16` runs `SELECT min(id) FROM core.locations WHERE country_iso = ? AND location_type = 'Country'` once per joined row. No index covers it. The index is not partial on purpose: SQLAlchemy sends `'Country'` as a bound parameter, and a partial index cannot serve a generic plan whose predicate value is a parameter.

**Files:**

```python
"""Locations: an index for the lookup of a country by its code (WP-44).

The Prompts page and the metrics planner read a prompt's place as the smallest location id of
its country (`idraft.keywords.prompt_links.prompt_location_id`), once per joined row. With
270,000 locations and no index on the code, 86 prompts cost 4 seconds. The index is not
partial: the type arrives as a bound parameter, which a partial index cannot serve in a generic
plan. The table is reference data the worker rewrites rarely, so the build blocks nobody.

Revision ID: 0040
Revises: 0039
"""

from __future__ import annotations

from alembic import op

revision: str = "0040"
down_revision: str | None = "0039"
branch_labels: str | tuple[str, ...] | None = None
depends_on: str | tuple[str, ...] | None = None


def upgrade() -> None:
    op.execute(
        "CREATE INDEX locations_country_type ON core.locations (country_iso, location_type, id)"
    )


def downgrade() -> None:
    op.execute("DROP INDEX core.locations_country_type")
```

### Task 2: More connections and a second API process

The pool is 10 with no overflow, in one process. `Settings.db_pool_size` (`backend/src/idraft/config/settings.py:139`) already reads `DB_POOL_SIZE`, so the size needs no code. Two workers are safe: sessions, throttles and locks live in Redis; the only in-process state is the password-hashing semaphore and a lint cache, both correct per process. Budget: 2 workers x 15 connections + 10 for the worker = 40 of PostgreSQL's 80.

**Files:**
- Modify: `infra/vps/systemd/idraft-api.service`
- Modify: `infra/vps/provision.sh` (the `api.env` heredoc, about line 107)
- Modify: `docs/ops/release-and-deploy.md`

**Precondition, checked 2026-11-26: two workers are safe.** The lifespan in `backend/src/idraft/api/main.py:224` builds the engine, Redis client and HTTP client per process. Sessions (`auth/sessions.py`) and login throttling (`auth/throttle.py`) live in Redis. The only module-level cache is `passwords.py:64`, a per-process dummy hash. Other dicts are per request (`taxonomy/service.py:557`). Background tasks are per request. Nothing in the API keeps state that two processes would disagree on. Releases do not install this unit: `infra/vps/activate.sh` writes only the `release.conf` drop-ins and `ship.sh` installs only `activate.sh`, so the unit change stays inert until it is applied by hand (Step 5).

### Task 3: Move OS updates to the night

The restart itself is inferred, not logged: no `needrestart` line was found, but PostgreSQL links the Kerberos libraries, and the timing is one second apart. Treat the cause as likely. ## Profile result (Task 5, 2026-11-26)

45 seconds, both API workers, while the AI Overview, Prompts and Citations pages loaded; 778 active samples. SQL is not the cost: `sqlalchemy` is 11.6% of leaf time and `asyncpg` 1.7%. About 46% of samples were inside request handling, and of all samples:

| Share | Where |
|---|---|
| 27.0% | `prompts_summary` (`api/ai/summary_routes.py`), so about 58% of request time |
| 18.1% | `_engine_row` in `api/ai/summary.py`; 17.2% in `_prompt_row` (they overlap) |
| 13.8% | pydantic `BaseModel.__init__`, building the response models row by row (`_cell`, `_week`, `point`, `cells`) |
| 5.3% | `TypeAdapter.dump_json`, serializing the response |
| 5.7% | `citation_gaps` (`api/ai/citation_board.py`) |

So the CPU goes to building thousands of small pydantic models in `summary.py` for every `prompts-summary` call, and the AI Overview sends about 9 of those calls per load. Phase 3 (one summary per load) cuts that work by the number of variants merged. Cheaper per-call work (building cells as plain dicts, or `model_construct`) is a second lever; it changes response validation, so it needs its own review.

## Phases 3 to 5: one plan each

These touch the API contract and the web app, and their shape depends on the profile. Each produces working software on its own.

| Phase | Change | Expected gain | Depends on |
|---|---|---|---|
| 3. One summary per AI Overview load | The cards in `apps/web/src/features/ai-overview` send about 9 `prompts-summary` variants that differ in `include` and `rows` (call sites listed in `use-overview-reads.ts:109-140`). Send one superset request (`include=entities,series,total,co_mentions`, `rows=topics`) and select from it per card. The freshness read uses a 92 day window and stays separate. | About 7 fewer requests per load; the pool pressure that caused the 500s goes away | Profile result; API contract review |
| 4. Keyword counts in one request | `apps/web/src/features/rankings/strip/strip-queries.ts:53-61` and `rankings-queries.ts:439-442` make 7 `tracked-keywords?limit=1` calls to read `total`. Plan written: `2026-11-26-keyword-strip-counts.md`. It adds `include=counts` to the existing list route instead of a new endpoint, so the 30 filter parameters are not duplicated. | 5 fewer requests and one fewer wave on the Keywords list | None |
| 5. Server prefetch of shell data | Only `/me` is hydrated (`apps/web/src/features/session/workspace-root.tsx:27-30`). Prefetch `engines`, `entities`, `runs?limit=1` and `alert-events` in the project layout over `API_INTERNAL_ORIGIN` and hydrate them, so the first browser wave starts with page data. | One fewer wave (250 to 450 ms) on every page | None |

Left for a decision by the owner, not planned here:

- **Cloudflare routing.** Requests go India to Marseille to India, about 220 ms each. Options: a paid Cloudflare plan with Argo routing, or DNS-only for `app` (which needs the firewall opened beyond Cloudflare's ranges and loses its protection).
- **Abandoned requests.** A request the browser cancels keeps running on the server and holds its connection. Cancelling it needs disconnect handling in each long handler; revisit after Phase 3 removes most of the long ones.
- **Redirects.** The project root and `/integrations` each redirect before rendering. Linking straight to the destination in the navigation removes the round trip.
