# Keywords Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Each task ends with: gates green (`backend/check.sh`), an independent review on the Opus model, fixes, commit.

**Goal:** Tracked keywords at scale: add them singly, in bulk or by CSV import with a preview, file them in groups and taxonomy terms, and keep their search volume, CPC, difficulty and intent current from DataForSEO Labs through the task ledger, with schedules, runs and a costs table to see what was spent.

**Architecture:** Step 5 of the build order, first part (`docs/29-phase-roadmap.md` section 1.1, Phase 3), specified in `docs/04-data-model.md` sections 7.1, 7.2 and 11.8, `docs/08-seo-keyword-system.md`, `docs/19-api-specification.md` sections 3.5 (term assignments), 3.6.1 to 3.6.3 and 3.11, `docs/06-dataforseo-seo-integration.md` sections 1 and 7, `docs/21-scheduler-workers.md` and `docs/27-cost-model.md` section 10. Keyword rules shared by the API and the worker (normalization, identity, quota, writing tracked keywords) live in a new package `sightline.keywords`, below the entrypoints. Labs is a live endpoint: the ledger gains a live path (one call answers a batch of tasks at once) next to the queued one, and an ingester that is the first to move tasks to `ingested`. Routes follow the existing packages: `routes.py`, `service.py`, `repository.py` per resource, every write in a workspace transaction under row-level security, every change audited.

**Tech stack:** nothing new. CSV parsing with the standard library `csv` module; object storage with the existing aiobotocore client (`sightline.storage`); `pg_trgm` (created by migration 0001) for keyword text search.

## Decisions

- **D1. Every new tenant table carries `workspace_id` and refers to its parents through `(id, workspace_id)`.** This holds for the link tables doc 04 left without the column (`tracked_keyword_config_history`, `keyword_group_members`, `tracked_keyword_terms`, `tracked_keyword_competitors`, `keyword_metrics_current`, `keyword_import_rows`), so row-level security and the catalog rule of `tests/db/test_rls.py` cover them, as in step 4 (doc 04 updated). Parents gain `UNIQUE (id, workspace_id)`.
- **D2. The API hard-deletes link rows.** These are group members, term assignments and competitor overrides, plus a group (its subgroups cascade, members are unlinked). Doc 04 section 13.1's "nothing is hard-deleted" list is updated with them. Tracked keywords are soft-deleted (`deleted_at`).
- **D3. Adding an identity that was deleted brings its row back.**
  - The identity key `(project_id, keyword_id, search_engine, location_id, language_code, device)` includes deleted rows, so history stays on one id.
  - The row's `deleted_at` is cleared and `is_active` set. Its stored settings stay as they were, whoever adds it back (API or import); a change of settings is a separate PATCH.
  - An archived identity (`is_active = false`) is `409 duplicate` with `existing_id`; unarchiving is a bulk-archive call.
- **D4. The quota counts active tracked keywords, one per row.**
  - Every way of adding or unarchiving takes a per-workspace advisory lock (the worker may read the quota row but not lock it), counts, and refuses the whole request when it would go over (`422 quota_exceeded` with `limit`, `used`, `requested`).
  - `device: 'both'` makes two rows and counts two.
  - The keywords of a deleted project no longer count; an archived project's still do, so bringing a project back never takes the workspace over its limit. Nothing is written into a deleted project.
- **D5. `core.urls` arrives now, written by the API for target URLs.**
  - It is a global dictionary like `core.domains` (no workspace, no row-level security), keyed by `url_hash` of the canonicalizer v1.
  - The API may insert rows (canonical URL, hash, domain, path) and read them; SERP ingest (second part) writes the rest.
  - A target URL that is not http(s) or does not canonicalize is `422` with `invalid_url`.
- **D6. Labs is called live, through the ledger.**
  - **Tasks.** A `keyword_metrics` task is one keyword at one location and language: subject type `keyword`, subject id `<keyword_id>:<language_code>`, `location_id` in its column.
  - **Batching.** The dispatcher batches live tasks like queued ones, up to the endpoint's batch size (700). The adapter makes one `keyword_overview/live` call per location and language in the batch.
  - **Raw payload.** The call's answer is stored once as a raw payload (retention class `serp_raw`) that every task of the call names.
  - **Cost.** The call's reported cost is split evenly over its tasks, to the micro-dollar, with the remainder on the first task. Each task gets one cost event with `cost_source = 'provider_reported'` and `units = 1`, `price_unit = 'item'`.
  - **Task states.** Tasks go `pending`, `submit_unknown`, `fetched` (`ready_source = 'live'`), then `ingested`.
  - **Failures.** A failed call follows the retry policy per task. A timeout counts as an attempt and is retried, because a live call has no result to fetch later.
  - **As built (Task 6 and its review).** Workloads give the dispatcher a batch key (`Workload.batch_key`); keyword metrics uses the location and language, so a batch is one Labs call. The adapter refuses on its own, without sending, a request for another endpoint, a task id given twice, and a keyword over 80 characters (`labs.accepts`; the workload leaves such keywords out). Keywords are escaped like SERP keywords (`%`, `+`), a keyword Labs reads as another one in the call is sent once, and both tasks get the answer. A 40102 "no results" answer is read as Labs knowing none of the keywords. A reported cost above $1.00 a call is not believed (the estimate is charged). `LiveResult.call_id` is the Labs task id. The resolver sends live tasks left in `submit_unknown` again after its grace period, whatever `resolve_unknown_submissions` says, since there is nothing to look for.
- **D7. The ingester writes one snapshot per task, even when Labs knows nothing.**
  - **No data.** A keyword missing from the answer gets a snapshot with every metric null, so it is not asked for again until the next refresh.
  - **`source` and `data_month`.** `source` is `dataforseo_labs`. `data_month` is the newest month in `monthly_searches`.
  - **`is_material_change`.** It is true for a keyword's first snapshot, and otherwise follows doc 06 section 7.2:
    - volume moves by more than 20% and more than 10 searches;
    - difficulty moves by more than 5 points;
    - or the main intent changes.
  - **Current metrics.** `seo.keyword_metrics_current` is upserted from the snapshot.
  - **Intent details.** Labs `keyword_overview` gives `main_intent` and `foreign_intent[]` without probabilities, so `intent_detail` stores `{"main": ..., "foreign": [...]}`. Probabilities wait for the `search_intent` endpoint.
  - **`competition`.** It is the Labs float; `competition_level` is the Labs string (doc 06's type trap).
- **D8. New keywords get metrics within minutes; the rest once a month.**
  - **New keywords.** A worker tick every 60 seconds finds keywords that are tracked actively, have no snapshot at that location and language, and have had no `keyword_metrics` task in the last 24 hours, finished or not. That way a keyword whose task failed is not paid for every minute. It creates one run per project: trigger `manual`, `created_by_type = 'system'`, which the manual-run limit does not count.
  - **Monthly refresh.** The first tracked keyword of a project creates the project's `keyword_metrics` schedule:
    - monthly, on the 20th;
    - 03:00 in the project's time zone, a 2 hour window;
    - provider mode `live`, selector `{"stale_days": 25}`.
  - Users can change or pause that schedule like any other.
- **D9. Manual and system runs are planned by the worker.**
  - `POST {P}/keyword-metrics/refresh` inserts a run in status `planned` with its selector in `config_snapshot` (the API cannot write tasks).
  - The planner plans planned manual runs as it plans due schedules, through the same workload code, budget check and ledger.
  - The manual-run limit is 20 per project per day, counted over runs created by users.
  - Cancelling a run sets its status; the reconciler cancels its pending tasks within its next pass (it already cancels the tasks of ended runs), so the API needs no write on tasks.
  - **As built (Task 7).** The plan tick runs, in order: the new-keyword tick, the planned manual runs, then due schedules. A manual run's window is one hour from when it is planned, and every task in it is due at once, so a project's keywords at one location and language go in one call. A manual run whose project no longer collects is cancelled (`project_not_collecting`); one over a used-up budget is `budget_blocked`, as a schedule's would be, and the new-keyword tick makes no other run for the project for 24 hours after one is blocked. A manual run no worker can plan (keyword metrics are registered only with DataForSEO credentials) is cancelled after 10 minutes (`workload_unavailable`). Its `config_snapshot` is the plan's (adapter, provider mode, source) with the selector it was asked with. Keyword metrics count against the `keyword_research` budget group. The selector takes `keyword_ids`, `stale_days`, `new` (keywords with no metrics, used by the new-keyword tick) and `all`; keywords over 80 characters are never planned. The location code sent is the provider map's, else the location id. The plan tick's three steps run even when one fails, and the tick then reports the first failure.
  - **As built (Task 7, ingest).** An ingest tick reads fetched tasks every 30 seconds, one stored answer per transaction. An answer that is not a Labs answer fails its tasks (`unreadable_answer`). One that cannot be read from storage (`answer_not_read`) or written (`answer_not_written`) waits 5 minutes, out of the passes in between, and its tasks fail once they were fetched a day ago, so their run can finish. A keyword Labs knew nothing of (missing from the answer, or named with no value) gets an empty snapshot that is no material change and does not replace current metrics; a keyword with no current metrics gets an empty current row. A reading is judged against the latest non-empty snapshot fetched before it, so an older answer ingested late is judged against what came before it. Months outside 2000 to 2100 are left out of `monthly_searches`. The selectors `groups` and `terms` arrive with schedules in Task 8.
- **D10. Schedules accept `daily`, `weekly` and `monthly`; `month_day` joins the schedule body.**
  - `cron` is `422` with `cadence_not_supported`, since the planner has no cron rule.
  - The workloads offered are `keyword_metrics` and `seo_rank`, the ones this step and the next run. Others are `422` with `workload_not_available`.
  - Selectors are checked per workload:
    - `keyword_metrics`: `stale_days`, `all`, `groups`, `terms`;
    - `seo_rank`: `all`, `groups`, `terms`, `priority_lte`.
  - Deleting a schedule sets `deleted_at`, so its runs keep naming it; a schedule tracked keywords name is `409 schedule_in_use`. A tracked keyword names a schedule of its own project (the key carries the project).
- **D11. An import keeps every source as an object, and the worker does the work.**
  - **Sources.** Paste text, JSON rows (up to 10,000) and a CSV upload (multipart, up to 50 MB, the one route above the 1 MB body limit).
  - **Storage.** Each source is written by the API to the raw bucket under `imports/v1/<workspace>/<import>/source`. R2 becomes an API setting too.
  - **Processing.**
    - A `parse_import` job on the `process` queue fills the rows and the preview.
    - Confirming starts a `write_import` job that writes in batches of 1,000 rows, one transaction each.
    - New keywords then reach D8's tick.
  - **Report.** It is a CSV streamed from the rows on request, not a stored object.
  - **Expiry.** Previews expire after 7 days (`expires_at` on the import).
- **D12. The import outcomes are fixed.**
  - **`new`:** the identity is not in the project.
  - **`duplicate`:** the identity is live in the project (action `skip`, or `merge` to add the row's groups and terms), or the row repeats an earlier row of the file (action `skip`, its groups and terms joined onto the first).
  - **`variant`:** the keyword exists in the workspace typed differently, for example "CRM Software" against "crm software". Action `create`, with a warning. The provider keeps receiving the first casing.
  - **`conflict`:** the identity is archived in the project (action `skip`, or `merge` to unarchive it).
  - **`invalid`**, with `reason_code`:
    - `keyword_missing`, `keyword_invalid` (a control character), `keyword_too_long` (over 700 characters), `search_operator_not_allowed`;
    - `location_unknown`, `language_invalid`, `device_invalid`, `priority_invalid`, `depth_profile_invalid`;
    - `target_url_invalid`, `group_path_invalid`.
  - **`device = both`:** expands to two rows that share the file's `row_no`, told apart by `part` (1 for desktop, 2 for mobile). The key is `(import_id, row_no, part)`, so a report lists them in file order.
  - **Not offered:** `force_separate` is `422` with `force_separate_not_available`, because doc 08 puts case-sensitive keywords in Phase 5.
  - **Mapping to `source`:** `upload` gives `csv_import`, `paste` gives `bulk_paste`, `api` gives `api`.
- **D13. Import columns follow doc 08 section 3.2, minus `competitors`.**
  - **`tags` and `topic`:** they name terms of vocabularies the import chooses in its options (`tags_vocabulary_id`, `topic_vocabulary_id`). Terms that are missing are created there at confirm, by the taxonomy rules of step 4. That takes `taxonomy:write`, so a member limited to some projects may only name their projects' vocabularies. Term writes to one vocabulary run one at a time: the API and the worker both take a per-vocabulary advisory lock, since the worker may not lock the vocabulary row.
  - **`group`:** a group path; groups that are missing are created.
- **D14. Costs are rolled up hourly, read from the rollup.**
  - **Rollup.** The `cost_rollup` job recomputes `ops.cost_daily` for today and yesterday (UTC) from `ops.provider_cost_events`, as a full replacement of those days, so it is safe to run twice.
  - **Reading.** `GET {W}/costs` groups the rollup; `meta.cost_sources` is summed from the events of the period.
  - **Price book.** It is seeded with the verified Labs prices of doc 27 section 1, with `source_url` and `verified_at`; the SERP prices come with rank collection, their first reader. It gives the workloads their estimates and nothing else (doc 04 section 11.3).
- **D15. The tracked keyword list in this step.**
  - **Filters:** `q`, `group`, `term`, `term_in`, `device`, `location_id`, `language_code`, `search_engine`, `intent_in`, `funnel_stage_in`, `priority_lte`, `is_active`, `source_in`, `depth_profile_in`, `search_volume_gte`, `keyword_difficulty_lte`.
  - **Sorts:** `keyword`, `search_volume`, `keyword_difficulty`, `cpc_usd`, `priority`, `created_at`.
  - **`include`:** `metrics`, `groups`, `terms`, `competitors`.
  - **Pagination:** a cursor, with `page.total` always.
  - **Missing metrics:** metrics come from the Labs current row. A sort on a metric puts keywords without one last, in both directions.
  - **Rank fields** arrive with rank collection.
