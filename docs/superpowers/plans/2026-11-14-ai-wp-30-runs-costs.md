## 3. Backend design

Statements: every statement carries `workspace_id` (and `project_id` for the project routes) as well as RLS.

- `GET {P}/runs/{run_id}/ai-coverage` (`B/api/operations/ai_coverage.py`, new, with `ai_coverage_repository.py`): S1 the run row (workspace, project, id; gives workload and `created_at`); S2 one grouped statement: tasks of the run (`run_id` index) LEFT JOIN current answers (`collection_task_id` plus `observed_at >= run.created_at` so only the right partitions are read), grouped by `engine_code`, with `count(*)` planned, `count(obs.id)` observed, and `count(*) FILTER (WHERE obs.status = ...)` for the five statuses; S3 the missing tasks (tasks with no answer, joined to `ai.prompt_versions` for the prompt id). Three statements whatever the run's size; the test asserts equality for 4 and 40 tasks and a ceiling.
- `GET {P}/ai/collection/daily` (`B/api/operations/collection_daily.py`, `collection_daily_repository.py`): S1 project zone; S2 enabled engines; S3 tasks grouped by `(local day of scheduled_for, engine)`; S4 answers grouped by `(local day of observed_at, engine)` with the five status counts and `array_agg(DISTINCT collection_run_id)`; S5 blocked runs by `(local day of completed_at)` with the engines from `config_snapshot`. `observed_date` and `observed_at` bounds make the partitions and `observations_project_engine_date` do the work. Python fills the dense rows. Five statements for 7 or 92 days and 1 or 3 engines.
- Budgets (`B/api/operations/budgets.py` service, `budgets_repository.py`, routes in `cost_routes.py`): plain statements, one per request plus the audit insert; `limit_usd` as `Decimal`, quantized to two places for `numeric(14,2)`.
- Forecast and unit costs (`B/api/operations/costs_forecast.py`, `costs_unit.py`, repository functions in `costs_repository.py`): unit costs: S1 visible projects, S2 grouped answers by `(project, engine)`, S3 grouped `cost_daily` by `(project, workload)`, S4 active prompts and active tracked keywords by project (one statement with two grouped sub-selects). Forecast: per project the planner's own reads, a constant count per project.
- Money: `Decimal` from the database (`Numeric`), division only through one helper `per_unit(total, count) -> Decimal | None` in `costs_unit.py` (None when `count == 0`), rounded once with `money()`. No float.
- Errors: `NotAnAiRunError` (`collection_errors.py`); `WindowTooLargeError`, `NotFoundError`, `DuplicateError` exist in `problems.py` (not edited).
- Schemas: `B/api/schemas/ai_collection.py` (edit: C3 change), new `B/api/schemas/budgets.py` (`BudgetCreate`, `BudgetUpdate`, `BudgetResponse`, `BudgetPage`, `ForecastRow`, `ForecastResponse`, `UnitCostRow`, `UnitCostResponse`; imports `Budget` and `Usd` from `operations.py`).
- Migration: none. The needed indexes exist (`collection_tasks (run_id)`, `observations_one_per_task`, `observations_project_engine_date`, the budgets unique constraint). If a measured plan shows a missing index, the implementer reports it instead of adding a migration (numbers 0023 or higher would be needed).
- Boundaries: `idraft.api` may import `idraft.collectors.ai_prompt` and `idraft.domain.*` as `runs.py` already does; `lint-imports` must stay green.
