Date: 2026-11-24. Roadmap: `2026-11-24-seranking-high-value-roadmap.md`. Specs already in the repo: docs/04 11.5 (tables),
docs/19 3.11.5 (routes), docs/08 12 and docs/11 10 (rule types and anti-spam), WP-47 and WP-48 in

## Owner decision (2026-11-24)

Version 1 is **in the app only, evaluated after each run**. No email, Slack or webhooks. The rule keeps the spec's
`channels` and `digest_mode` columns (values `in_app` and `immediate` only), so email and Slack plug in later as a daily
digest without a migration. Email waits for the mail sender decision of Reports (feature 1).

## Rule types in version 1

| Rule type | Fires when | Facts it reads |
|---|---|---|
| `ai_mention_gained` | the brand is mentioned in an answer set for a prompt and was not in the previous run | `ai.observation_facts.own_mentioned` |
| `ai_mention_lost` | the reverse | same |
| `ai_competitor_appeared` | a competitor is mentioned for a prompt and was not in the previous run | `competitor_mentions` |
| `rank_drop` | a keyword's rank fell by at least `positions` (default 5) in one check | `seo.rank_events` event_type `rank_drop` |

"Run to run" compares, per prompt and platform, the share of valid answers that mention the entity in this run with the
previous run. The entity counts as present when at least one valid answer mentions it (same rule as the Compare days
model). A prompt needs a valid answer in both runs, otherwise nothing fires (unknown is never zero). Detection reads
stored facts only. It makes no provider call.

Dropped from version 1 (spec rows kept for later): panel change, citation lost or gained, share of voice overtake, new
source, model changed, collection degraded, hold and flapping mute, digests, webhook endpoints.

## Data and detection

- Migration 0035 creates `ops.alert_rules` and `ops.alert_events` as in docs/04 11.5 (RLS, grants, `workspace_id`),
  plus `ops.alert_state` (`rule_id`, `last_run_id`) is NOT added: the watermark is `alert_events.occurred_at` and the
  run's `completed_at`, kept in one row per project in `ops.alert_cursors (project_id, last_completed_at)`.
- `idraft/alerts/detect.py`: pure functions. `mention_changes(previous, current)` and `rank_drops(events, positions)`
  return `EventDraft`s. Tested without a database.
- `idraft/alerts/evaluate.py`: a worker tick `evaluate_alerts` (like `rank_ingest`). It finds runs completed after the
  project's cursor, loads active rules, runs detection per rule scope, inserts events with the dedupe key
  `rule|subject|kind|run_id` (`ON CONFLICT DO NOTHING`), then moves the cursor. Idempotent.
- Hold-ups on a run (failed answers) are honoured by the valid-answer rule above.

## API (version 1 subset of docs/19 3.11.5)

`GET /api/v1/alert-rule-types`, `GET|POST {P}/alert-rules`, `GET|PATCH|DELETE {P}/alert-rules/{id}`,
`GET {P}/alert-events` (cursor, filters `acknowledged`, `rule_id`), `POST {P}/alert-events/acknowledge`.
Access lines in `test_route_access.py` and `_TENANT_ROWS` entries in `test_cross_tenant.py`. The `/test` and `/preview`
routes wait for email and Slack.
